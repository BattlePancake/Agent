**Producer:** Skill requirement-review
**Status:** Reviewed
**Date:** 2026-09-08

## Scope

Функциональность «Авторизация пользователя»: система предоставляет зарегистрированным пользователям возможность авторизации по email и password.

## Requirements

| ID | Требование | Source |
|----|------------|--------|
| R1 | Пользователь может авторизоваться по email и паролю. | REQ-1 |
| R2 | Email должен принадлежать зарегистрированному пользователю. | REQ-2 |
| R3 | При вводе неправильного пароля система должна отображать сообщение об ошибке. | REQ-3 |
| R4 | После нескольких последовательных неуспешных попыток авторизации учетная запись пользователя должна быть временно заблокирована. | REQ-4 |
| R5 | После успешной авторизации пользователь должен быть перенаправлен на главную страницу. | REQ-5 |
| R6 | Поля Email и Password являются обязательными. | REQ-6 |
| R7 | Email должен иметь корректный формат. | REQ-7 |
| R8 | Пароль должен соответствовать требованиям безопасности системы. | REQ-8 |
| R9 | Заблокированный пользователь не должен иметь возможности авторизоваться. | REQ-9 |
| R10 | Система должна обеспечивать безопасную обработку учетных данных пользователя. | REQ-10 |

## Business Rules

- BR-1: Учетная запись блокируется после последовательности неуспешных попыток авторизации (конкретное количество не задано) — следует из R4.
- BR-2: Заблокированная учетная запись исключает возможность авторизации — следует из R9.
- BR-3: Для авторизации email должен принадлежать зарегистрированному пользователю — следует из R2.

## Acceptance Criteria

Явно определенные Acceptance Criteria отсутствуют в исходных требованиях. Отдельные требования (R3, R5, R9) содержат наблюдаемый результат, но формальных критериев приемки нет.

## Validation Rules

- VR-1: Поля Email и Password обязательны (R6).
- VR-2: Email должен иметь корректный формат (R7).
- VR-3: Пароль должен соответствовать требованиям безопасности системы (R8, конкретная политика не задана).
- VR-4: Отображается сообщение об ошибке при неверном пароле (R3).

## Dependencies

- DEP-1: R2 и R4-R9 зависят от наличия зарегистрированных пользователей (сущность «зарегистрированный пользователь» должна существовать).
- DEP-2: R4 и R9 зависят от механизма отслеживания состояния попыток авторизации и статуса блокировки учетной записи.
- DEP-3: R10 зависит от инфраструктуры безопасного хранения и передачи учетных данных.

## Ambiguities

- AMB-1: «Несколько последовательных неуспешных попыток» — количество попыток, после которого блокируется учетная запись, не определено.
- AMB-2: «Временно заблокирована» — продолжительность блокировки и условия разблокировки не определены.
- AMB-3: «Требованиям безопасности системы» (R8) — конкретная политика паролей (длина, символы) не определена.
- AMB-4: Поведение при вводе email незарегистрированного пользователя не специфицировано: требования не описывают отображаемое сообщение/поведение для этого случая (специфицирована только ошибка неверного пароля, R3).
- AMB-5: R10 «безопасную обработку учетных данных» — не определены конкретные операционные меры (хэширование, шифрование при передаче, отсутствие логирования паролей и т.п.).
- AMB-6: Формат email (R7) не определен (какой именно формат/регулярное выражение считается корректным).

## Missing Information

- MI-1: Количество неуспешных попыток до блокировки.
- MI-2: Длительность блокировки и способ разблокировки (автоматическая/ручная).
- MI-3: Политика паролей (минимальная длина, требования к символам).
- MI-4: Определение корректного формата email.
- MI-5: Тексты сообщений об ошибках (включая поведение при незарегистрированном email).
- MI-6: Определение «главной страницы» для редиректа (R5).
- MI-7: Конкретные требования к безопасной обработке учетных данных (R10).

## Conflicts

Явных внутренних противоречий между требованиями не обнаружено.

## Positive Flows

- PF-1: Ввод зарегистрированного email и корректного пароля → успешная авторизация → редирект на главную страницу (R1, R2, R5).
- PF-2: Валидация обязательных полей и форматов проходит успешно для валидных данных (R6, R7, R8).

## Negative Flows

- NF-1: Неверный пароль → отображение сообщения об ошибке, авторизация не выполняется (R3).
- NF-2: Пустое поле Email или Password → авторизация отклоняется (R6).
- NF-3: Некорректный формат email → авторизация отклоняется (R7).
- NF-4: Пароль не соответствует требованиям безопасности → авторизация отклоняется (R8).
- NF-5: Email незарегистрированного пользователя → авторизация отклоняется (R2; поведение/сообщение не специфицировано, см. AMB-4).
- NF-6: Последовательные неуспешные попытки → учетная запись временно блокируется (R4); заблокированный пользователь не может авторизоваться (R9).

## Boundaries

Значимые граничные условия не могут быть определены без отсутствующей информации:

- Порог блокировки (количество попыток) — недостаточно данных (MI-1).
- Политика паролей — недостаточно данных (MI-3).
- Определение корректного формата email — недостаточно данных (MI-4).

## Risks

- RSK-1: Неопределенный порог блокировки может привести к DoS для легитимных пользователей (AMB-1, MI-1).
- RSK-2: Неопределенная политика паролей создает риск слабых учетных данных (AMB-3, MI-3).
- RSK-3: Размытые требования к безопасной обработке учетных данных создают риск безопасности (AMB-5, MI-7).
- RSK-4: Отсутствие спецификации поведения для незарегистрированного email может привести к расхождению в реализации (AMB-4).
- RSK-5: Отсутствие формальных Acceptance Criteria повышает риск неоднозначного понимания готовности (см. Acceptance Criteria).

## Open Questions

- OQ-2: На какой срок блокируется учетная запись и как происходит разблокировка?
- OQ-3: Какие требования к паролю считаются требованиями безопасности системы?
- OQ-4: Какое сообщение/поведение должно быть при вводе незарегистрированного email?
- OQ-5: Что именно подразумевается под «безопасной обработкой учетных данных»?
- OQ-6: Какие тексты сообщений об ошибках должны отображаться?
