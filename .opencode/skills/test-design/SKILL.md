## Purpose
Skill проектирует риск-ориентированную тестовую модель на основании проверенного Requirement Review / Jira Tasks и формирует **Test Model Artifact**, предназначенный для последующего автоматического создания тестовых сущностей через Qase Tool).

Skill занимается исключительно проектированием тестов. Он не выполняет тестирование и не создает сущности в Qase напрямую.

## Inputs
### Обязательные входные данные:
* **Валидный Requirement Review Artifact** и список созданных задач в Jira с их Summary, Description и Acceptance Criteria.

### Опциональные входные данные:
* Ограничения тестирования.
* Релевантные существующие тест-кейсы (полученные через Qase Tool для анализа покрытия).
* Проектные правила приоритезации.
* Дополнительный Context, явно переданный агентом.

## Context Management
* Используй Requirement Review как основной вход для тест-дизайна, а Jira Tasks только для синхронизации ID (Traceability) и объемов (Scope) поставки . Не анализируй заново весь Confluence, если информация уже есть во входных данных.
* Текст и логика тестовых сценариев должны строго соответствовать тому, что уходит в разработку через Jira/Acceptance Criteria. Не придумывай шаги, если логика в требованиях неполная.
* Используй существующие тест-кейсы Qase только для анализа текущего покрытия, предотвращения дублирования и определения тестов, требующих актуализации.
* Не вызывай Qase Tool самостоятельно: все Tool-вызовы выполняются вышестоящим агентом.

## Procedure
1. Каждое бизнес-правило, функцию и пункт из Acceptance Criteria преврати в один или несколько тест-сценариев.
2. Оцени риски и бизнес-критичность для применения risk-based подхода.
3. Выдели Positive Scenarios, Negative Scenarios, покрой Validation Rules и значимые Boundary Conditions.
4. Для каждого сценария сформулируй Preconditions, пошаговые действия (Steps) и **Expected Result для каждого конкретного шага**.
5. Назначь сценарию Priority, Severity, Type, Behavior и Automation Status.
6. Свяжи каждый сценарий с Source Requirement и ID (Key) связанной задачи Jira.
7. Сформируй итоговый Test Model Artifact и проверь его по Completion Criteria.

## Rules
* 1 тестовый сценарий должен проверять 1 логически завершенное действие или правило. Избегай перегруженных сценариев (более 10 шагов).
* Сценарии не должны жестко зависеть от выполнения друг друга. Используй для этого понятные и автономные Preconditions.
* Не придумывай бизнес-поведение, которого нет в требованиях/Jira. Допускаются risk-based проверки, но они должны быть явно обозначены как `QA/Risk-based`, а не как бизнес-требование.
* Если логика требований кажется неполной или содержит Ambiguities/Conflicts, не выдумывай Expected Result. Зафиксируй открытый вопрос и пометь зависимые сценарии специальным статусом.
* Не вызывай Qase Tool и не считай тест-модель фактически созданной в Qase до подтверждения со стороны Tool на уровне агента.

## Reasoning Patterns
* **Self-Refine / Critic (Основной):** Шаблон проверки качества Test Model по схеме: *Generate - Evaluate - Improve - Evaluate*. Агент обязан критически проверить полноту покрытия, негативные сценарии, границы, ожидаемые результаты шагов, приоритеты и трассировку.
* **Branching / Tree:** Используй только при наличии существенно разных тест-стратегий, влияющих на риски, стоимость или время. Сравни не более 3 вариантов и выбери оптимальный.
* **Reviewer:** Если Workflow включает независимый ревью, передай ему только валидный Test Model Artifact и ссылки на требования, а не всю историю рассуждений.

## Output: Test Model Artifact
Сформируй упорядоченный структурированный артефакт. Для каждого тестового сценария обязательно укажи:

* **Local ID:** Внутренний идентификатор сценария.
* **Suite Name / Path:** Целевой тест-сьют для размещения.
* **Action Type:** `Create New` (создать новый) или `Update Existing` (редактировать существующий с указанием ID старого кейса).
* **Title:** Короткий, лаконичный, проверяемый заголовок.
* **Source Requirement / Jira Issue ID:** Traceability-ссылка на требование и задачу в Jira (например, *PROJ-123*).
* **Preconditions:** Стартовое состояние системы (если применимо).
* **Steps & Expected Results:**
  * Шаг 1: [Действие] -> Ожидаемый результат 1
  * Шаг 2: [Действие] -> Ожидаемый результат 2
* **Priority:** `HIGH` / `MEDIUM` / `LOW`.
* **Severity:** `BLOCKER` / `CRITICAL` / `MAJOR` / `MINOR`.
* **Testing Type:** `Functional` / `Smoke` / `Regression`.
* **Behavior:** `Positive` / `Negative` / `Boundary` / `Risk-based`.
* **Automation Status:** `Manual`.
* **Risk Reference:** Описание риска (только для сценариев типа *Risk-based*).
* **Status / Blockers:** Оставь отметку `BLOCKED / REQUIRES_HUMAN_DECISION` и укажи `Open Question`, если сценарий зависит от нерешенной неоднозначности в требованиях.

## Artifact Contract
* **Producer:** Skill test-design.
* **Consumer:** Agent (этап создания тестовых сущностей в Qase через Qase Tool).
* **Artifact:** Test Model.
* **Validation:** Completion Criteria этого Skill.
* **Error Handling:** Если критическая часть требований заблокирована вопросами, исключи зависимые сценарии из готовой к созданию части Artifact, явно описав причину в блоке Blockers.

## Completion Criteria
1. Все критические подтвержденные требования и критерии приемки (Acceptance Criteria) из Jira-задач полностью покрыты.
2. Покрыты Positive, Negative, Validation Rules и значимые Boundary Conditions сценарии.
3. Каждый готовый сценарий атомарен, независим и содержит Expected Result для **каждого** шага.
4. Назначены Priority и Severity согласно бизнес-критичности и техническому влиянию.
5. Сохранена Traceability (связь) к требованиям и ID задач Jira.
6. Risk-based сценарии четко отделены от сценариев на основе бизнес-требований.
7. Необоснованные дубликаты тест-кейсов полностью отсутствуют.
8. Все нерешенные Ambiguities, Блокеры и Открытые вопросы явно видимы в артефакте.
9. Artifact полностью валиден, структурирован и готов к передаче агенту для имплементации через Qase Tool.
