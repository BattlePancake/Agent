## Purpose
Skill выполняет систематическое ревью требований, выявляет их структуру, неоднозначности и противоречия.
Результатом работы является проверенный Requirement Review Artifact, предназначенный для проектирования тестовой модели (в Qase/Test IT) и формирования задач разработки (в Jira) на последующих этапах Agent Workflow без необходимости повторного анализа исходного текста.

Skill отвечает только за анализ требований. Он не проектирует Jira-задачи, не создает тестовую модель и не выполняет действия во внешних системах.

## Inputs
### Обязательные входные данные:
* **Актуальные требования:** Текущая функциональность, полученная агентом из Confluence.
* **Source Reference:** Ссылка, идентификатор или иной reference на исходный источник требований.

### Опциональные входные данные (применяются только если они непосредственно относятся к анализируемому функционалу):
* Критерии приемки (Acceptance Criteria).
* Связанные бизнес-правила и ограничения.
* Релевантная связанная документация и подтвержденные проектные соглашения.
* Дополнительный Context, явно предоставленный агентом.

## Context Management
* **Strict Scope:** Используй только данные, относящиеся к анализируемой функциональности. Не используй требования других функциональностей.
* **Актуальность:** Не используй устаревшие версии требований, если доступна более актуальная версия.
* **Первоисточник:** Не используй предыдущие выводы агента как Source of Truth, если их можно проверить по исходным требованиям.
* **Фрагментация:** При большом объеме документации анализируй только релевантные фрагменты, переданные агентом.
* **Ограничение Tools:** Не загружай и не запрашивай самостоятельно данные из Jira или Qase. Внешние Tools управляются Agent Instruction. Skill не должен искать самостоятельно отсутствующие входные данные вне пределов переданного контекста.
* **Фиксация дефицита:** Если входного Context недостаточно, явно зафиксируй Missing Information.

## Procedure
При анализе требований необходимо последовательно выполнить следующие шаги:
1. Определить точный Scope анализируемой функциональности.
2. Выделить явно сформулированные функциональные требования.
3. Выделить бизнес-правила и ограничения.
4. Выделить Acceptance Criteria, если они явно определены.
5. Определить зависимости между требованиями и связанными функциями.
6. Найти неоднозначные формулировки, допускающие несколько интерпретаций (Ambiguities).
7. Найти внутренние противоречия между требованиями (Conflicts).
8. Определить отсутствующую информацию, необходимую для однозначного понимания ожидаемого поведения (Missing Information).
9. Выделить правила валидации и значимые граничные условия, если они следуют из требований (Validation Rules & Boundaries).
10. Определить основные Positive Flows и Negative Flows, прямо следующие из требований.
11. Определить QA-риски, связанные с реализацией и тестированием требований.
12. Сформировать Open Questions для спорных, противоречивых и неполных требований с приоритезацией (Блокирующие / Некритичные). Статус Блокирующего присваивать строго при наличии критических пробелов, без устранения которых невозможно продолжить работу с требованием.
13. Все обнаруженные пропуски данных, недочёты, противоречия и конфликты записать в Open Questions детально и атомарно.
14. Сформировать структурированный Requirement Review Artifact.
15. При наличии критических блокеров в Open Questions укажи статус BLOCKED в заключении артефакта.

## Rules
* **Запрет галлюцинаций:** Не придумывай отсутствующие требования, бизнес-правила, ограничения или Acceptance Criteria. Отсутствующая информация не должна выдаваться за подтвержденное требование.
* **Запрет домыслов:** Не выдавай предположение за подтвержденное требование. Не разрешай бизнес-неоднозначности самостоятельно.
* **Фиксация коллизий:** Если два авторитетных фрагмента противоречат друг другу, зафиксируй Conflict.
* **Трассируемость (Traceability):** Каждый существенный вывод, правило, поток или риск должен иметь явную связь с ID исходного требования или source reference.
* **Неизменяемость:** Не изменять исходные требования и исходный текст документов. Risk или Recommendation не должны подменять исходное Requirement.
* **Ограничение ответственности:** В рамках этого скилла не выполнять действия, не имеющие отношения к анализу требований: не создавать задачи в Jira, не создавать тест-кейсы и тестовую модель в Qase.

## Reasoning Pattern
### Self-Refine / Critic
После формирования первого варианта Requirement Review проверь его по Completion Criteria. Если обнаружены исправимые недостатки, уточни Artifact и выполни повторную проверку. Максимальное количество циклов исправления определяется Agent Instruction. Skill не должен инициировать бесконечное само-уточнение.

### Branching / Tree
Не применяется по умолчанию. Если требование допускает несколько существенно разных трактовок, Skill не выбирает одну ветвь, а фиксирует Ambiguity и варианты трактовки для эскалации.

## Output Structure & Data Contract
Результат должен быть строго структурирован (в формате Markdown с использованием системных заголовков), чтобы следующий этап мог использовать его автоматически.

### 1. Metadata Block
* **Timestamp:** [Дата и время анализа]
* **Source Version/Commit:** [Версия исходного документа из Confluence]
* **Artifact Version:** [Версия v.1]

### 2. Core Content
* **Scope:** [Границы анализируемого функционала]
* **Requirements:** [Список функциональных требований с уникальными ID]
* **Business Rules & Constraints:** [Бизнес-правила и технические ограничения]
* **Acceptance Criteria:** [Критерии приемки]
* **Validation Rules:** [Правила валидации данных]
* **Dependencies:** [Связи и зависимости между компонентами/требованиями]

### 3. Analysis & Gaps (со ссылками на ID требований)
* **Ambiguities:** [Найденные неоднозначности и варианты их трактовки]
* **Conflicts:** [Выявленные противоречия]
* **Missing Information:** [Отсутствующая информация с указанием критичности]
* **Open Questions:** [Список открытых вопросов для аналитиков/PO: Блокирующие / Некритичные]

### 4. Behavior & Quality Gates
* **Positive Flows:** [Сценарии успешного выполнения]
* **Negative Flows:** [Сценарии обработки ошибок и исключений]
* **Boundaries:** [Граничные значения для полей и логики]
* **Risks:** [QA и архитектурные риски]
* **Source References:** [Матрица соответствия выводов и ссылок на источники]

## Artifact Contract
* **Producer:** Skill `requirement-review`.
* **Consumers:** Skill `task-design` и Skill `test-design`.
* **Artifact:** Requirement Review Document.
* **Validation:** Completion Criteria этого Skill.
* **Error Handling:** Если обязательный вход отсутствует или критическая неоднозначность/блокирующий вопрос не позволяет сформировать надёжный Artifact, вернуть невалидный/заблокированный результат (Status: BLOCKED) с детальным описанием причины в секции `Missing Information`, а не заполнять пробелы предположениями.

## Completion Criteria
Skill считается успешно примененным, если:
1. Все предоставленные релевантные требования из Confluence полностью проанализированы.
2. Явные Requirements, Business Rules, Constraints и Acceptance Criteria выделены и структурированы.
3. Все Ambiguities и Conflicts детально и атомарно зафиксированы со ссылками на пункты, либо явно указано: *"Не обнаружено"*.
4. Вся Missing Information зафиксирована и классифицирована по уровням критичности.
5. Validation Rules и значимые Boundaries отражены везде, где они логически следуют из требований.
6. Positive и Negative Flows определены в полном объеме на основе доступных требований.
7. QA Risks и Open Questions зафиксированы, сформулированы тезисно и прозрачно.
8. Все существенные выводы имеют сквозные Source References к исходным ID требований.
9. Артефакт не содержит придуманных требований, домыслов AI или изменений оригинального текста.
